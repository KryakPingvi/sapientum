# Сервисы стенда и владение данными

Основание: [границы сервисов после ревью #10](decisions/03-service-boundaries.md). Самостоятельно запускаемые единицы — идентификация и турнир. Staff/teams остаются модулями сервиса турнира, чтобы не разрывать транзакцию проверки прав и записи команды. Это выбранный вариант из ревью, а не распределённая транзакция между staff и teams.

`npm run dev` собирает код, поднимает два PostgreSQL-контейнера и порождает отдельные Node-процессы. У каждого процесса свой пул, свой набор миграций и собственная БД. Идентификация применяет 003-sessions.sql, 004-session-maintenance.sql, каталог demo_accounts и таблицу ограничений входа; турнир — 001-staff.sql, 002-teams.sql и demo_tournaments. Аккаунты и сессии не читаются SQL-запросами турнира. При повторном старте новая случайная JWT-подпись требует повторного входа или refresh; внутри одного запуска ключ одинаков при перезапуске процесса в проверке.

Оставшиеся замечания ревью #11, лимиты ресурсов и конкретные проверки перечислены в [review-11.md](review-11.md). `DEMO_POOL_MAX` задаёт 1–50 соединений, по умолчанию 10. Process-check сначала использует max=1 для воспроизведения риска истощения пула, затем перезапускает auth с max=10 перед измерением конкуренции сессии. Пулы турнира в этой серии остаются max=1.

## Межсервисный контракт

Идентификация слушает loopback:3001 и принимает POST JSON не больше 16 KiB. Каждый вызов требует секретный X-Service-Key; браузеру он не отдаётся. Оркестратор генерирует его и ключ JWT в памяти и передаёт дочерним процессам через окружение. В реальном развёртывании нужны секреты из конфигурации и TLS/изоляция сети; известные демокреды не используются для production.

| Путь                     | Запрос               | Ответ                                                      |
| ------------------------ | -------------------- | ---------------------------------------------------------- |
| `/internal/account`      | `{ id }`             | `{ exists: boolean }`                                      |
| `/internal/authenticate` | `{ accessToken }`    | `{ userId, sessionId }` либо 401                           |
| `/internal/route`        | `SessionHttpRequest` | `SessionHttpResponse`, включая служебную cookie-инструкцию |

Турнир проксирует браузерные `/auth/*` в `/internal/route` после проверки Host, Origin и CSRF. Это локальная gateway-граница: SessionHttpRequest не принимается от браузера напрямую. Проверенный principal получают только из `/internal/authenticate`; роли не доверяются JWT/сети. Cookie остаётся HttpOnly/SameSite и принадлежит внешнему адресу турнира, а не внутреннему API.

Таймаут межсервисного fetch — 1500 мс. Отказ, таймаут или некорректный principal дают 503 SERVICE_UNAVAILABLE; защищённое действие не выполняется. Неверная/закрытая сессия даёт 401. Автоматических повторов мутаций нет: потеря ответа refresh не приводит к скрытому повторному использованию токена. Публичный GET команд не требует сервиса идентификации. Удаление аккаунта и запись заявки не имеют общего коммита; ID не переиспользуется, а доступность аккаунта проверяется при аутентификации. Реальная политика удаления аккаунтов ещё должна быть определена при реализации рабочего каталога.

## Самостоятельный запуск и реплики

После `npm run build` и `docker compose -p sapientum-demo -f infra/compose.dev.yaml up -d --wait` процессы можно запускать отдельно:

```powershell
# В каждой консоли одинаковые значения из своей конфигурации:
$env:DEMO_SERVICE_KEY = '<случайный общий секрет не короче 32 символов>'
$env:DEMO_JWT_KEY_BASE64 = '<32 случайных байта в base64>'
# Консоль 1:
npm run dev:auth
# Консоль 2, после готовности auth:
npm run dev:tournament
# Консоль 3, после первой реплики турнира:
$env:DEMO_PORT = '3002'
npm run dev:tournament
```

Для обычной проверки проще `npm run dev`, он сам задаёт секреты. `DEMO_AUTH_URL` задаёт адрес внутренней идентификации, по умолчанию http://127.0.0.1:3001. Разрешённые порты стенда: 3000/3002 для турнира, 3001 для идентификации. Каждая реплика проверяет собственный Host/Origin и CSRF; клиент сначала получает контекст с выбранной реплики. Cookie браузера общие между портами одного хоста. Нагрузочный инструмент работает явными Bearer-токенами, а не браузерными cookie.

## Что проверяется между процессами

`npm run dev:process-check` запускает настоящий auth и две реплики турнира. Через третье тестовое соединение БД удерживается строка команды, чтобы остановить уже допущенное подтверждение. Вторая реплика пытается снять роль; pg_locks подтверждает ожидание exclusive-lock за shared-lock первой. После освобождения строки подтверждение завершается, отзыв сохраняется, обе реплики отклоняют следующее подтверждение с 403. Это тест порядка реальных сетевых команд, а не замена HTTP проверкой интерфейса.

Затем auth принудительно останавливается: публичный список остаётся доступен, защищённый запрос получает 503. После перезапуска с тем же ключом/БД прежняя сессия работает. Logout через одну реплику отклоняется на другой. Проверяется отсутствие auth_sessions и demo_accounts в БД турнира. Для масштабирования выполняются одинаковые серии подтверждений через одну и две реплики; данные и границы измерения — в [performance.md](performance.md).

Стенд подтверждает выбранные процессные границы и сетевые отказы локально. Он не является production-развёртыванием, не реализует все рабочие места drawio и не доказывает достаточную производительность приёма фото. Рабочие каталоги аккаунтов/турниров, TLS, эксплуатационные настройки и нагрузка на сканы остаются отдельной работой.
