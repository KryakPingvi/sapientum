## 1. Auth и права турнира имеют разные границы

**Контекст.** На доске вход по логину и паролю, публичной регистрации нет, аккаунты создаются вне показанного процесса. Пять переключателей ролей относятся к оргкомитету турнира. Представитель работает с телефона, жюри — со своего рабочего места.

**Решение.** `auth` отвечает за идентичность аккаунта и доступность отдельного входа. `staff` отвечает за актуальные права внутри конкретного турнира. Публичного `/register` нет. Проверка пароля и доступности аккаунта подключается через `AccountCredentials` и `SessionAccounts`, реального каталога пока нет.

**Обоснование.** Исключение из оргкомитета одного турнира не является блокировкой аккаунта во всей системе. Сессии не дублируют роли и не становятся частью агрегата `StaffMember`.

**Проверка.** `removing tournament rights affects every device without expiring their JWTs or account sessions`.

## 2. JWT с серверной сессией

**Контекст.** Требуется завершать доступ устройства до истечения JWT и видеть список входов.

**Решение.** Один вход создаёт одну серверную сессию. JWT содержит `sub`, `sid`, `jti`, стандартные временные поля, issuer и audience. Подпись проверяет `jose`, алгоритм фиксирован HS256, тип `at+jwt`. После проверки JWT сервер читает сессию и доступность аккаунта, без кэша. Затем предметный модуль проверяет права в БД.

**Обоснование.** Только локальная проверка подписи оставила бы закрытому устройству доступ до `exp`. Серверная проверка отказывает при следующем запросе после коммита закрытия. Роли не остаются в устаревшем токене.

**Последствия.** Решение требует обращения к серверному хранилищу при запросе. Сбой БД не даёт доступ. Аппаратная привязка и распознавание физического устройства не заявляются: метка/IP/User-Agent — описание входа.

**Проверка.** `login creates independent persistent device sessions without JWT roles or raw stored refresh tokens`, `revoking one device rejects its existing access and refresh tokens while other devices keep working`, `JWT checks reject wrong signatures, claims, audience, issuer, type and nonexistent sessions`.

## 3. Настраиваемые сроки

**Решили сами.** По умолчанию JWT живёт 15 минут, бездействие сессии ограничено 7 днями, абсолютное время — 30 днями. `SessionPolicy` задаётся сервером; положительные целые сроки проверяются, access ограничен часом, абсолютный срок — 366 днями. Refresh и активность не переносят абсолютную границу.

**Обоснование.** Пользователь запросил регулировку сроков, на доске конкретных значений нет. Срок JWT не используется как задержка отзыва прав. Настройки не являются требованием стандарта и могут быть изменены при сборке сервера.

**Последствия.** Новая политика не переписывает сроки уже выданных JWT и сохранённых сессий. Для срочного отзыва нужно закрытие сессии, а не изменение числа в конфигурации.

**Проверка.** `access expiry is independent from idle and absolute session deadlines`, `idle sessions, expired refresh tokens and disabled accounts cannot regain access`, `session policies, key configuration and login metadata are validated`.

## 4. Ротация и обнаружение повторов refresh

**Решение.** Refresh — случайные 32 байта; в БД хранится SHA-256. У сессии история хэшей использованных и действующего refresh. Обновление берёт блокировку родительской сессии, затем перечитывает состояние токена и заменяет его. Повтор использованного токена отзывает всю сессию; транзакция коммитится до возврата 401.

**Обоснование.** История позволяет заметить повтор, а сохранение только хэша уменьшает последствия утечки БД. Прочитать состояние до ожидания блокировки недостаточно: конкурентный запрос может уже использовать токен.

**Последствия.** Два параллельных refresh одной сессии приводят к её закрытию. Клиент должен объединять обновления между вкладками; при потере ответа требуется вход. Другие устройства не затрагиваются. История сохраняется; плановая очистка должна учитывать абсолютные сроки и не удалять хэши действующей семьи токенов.

**Источники.** [RFC 9700, раздел 4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2) описывает ротацию и обнаружение повторов; этот модуль не заявляет реализацию всего OAuth.

**Проверка.** `refresh rotates tokens and a replay commits revocation of the whole token family`, `concurrent refreshes cannot both consume one token and replay revocation survives the error`.

## 5. Управление своими устройствами и конкуренция

**Решение.** Пользователь видит все свои сессии, их состояния, сроки и текущий вход. Может закрыть одну либо все, включая текущую. Чужая сессия не блокируется и возвращает 404. Для входа и отзыва используется блокировка аккаунта; для проверки, refresh и отзыва — строки сессии. Порядок при отзыве: аккаунт → текущая сессия → целевая собственная сессия.

**Обоснование.** Управление сессиями — право владельца аккаунта, а не роль организатора турнира. Сериализация предотвращает взаимную блокировку двух своих устройств при попытке закрыть друг друга. Поиск целевой сессии ограничен владельцем ещё в SQL.

**Последствия.** После завершённого logout refresh не может восстановить эту сессию. Уже допущенное предметное действие не отменяется; граница отзыва — следующая проверка. Для подтверждения команды дополнительно сохраняется существующая атомарность проверки роли и изменения.

**Источники.** [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) рекомендует просмотр и удалённое завершение собственных сессий, серверные сроки и серверную инвалидизацию.

**Проверка.** `sessions are private to their account and logout all closes every own device`, `concurrent refresh and logout cannot resurrect a closed session`.

## 6. HTTP-граница без регистрации и подмены principal

**Решение.** Framework-independent адаптер предоставляет login, refresh, список и DELETE сессий. `withSessionAuthentication` создаёт principal для маршрутов команд и оргкомитета. Refresh возвращается служебным полем cookie, не JSON. Хост применяет Secure/HttpOnly/SameSite, no-store, проверяет Origin и CSRF всех auth-мутаций, включая login. При непроверенном CSRF адаптер отказывает.

**Обоснование.** В проекте ещё нет HTTP-хоста, поэтому обязанности его интеграции заданы явно. Принимать аккаунт/сессию/результат CSRF из пользовательского JSON нельзя. Пароль передаётся проверяющему адаптеру без нормализации.

**Последствия.** Модуль реализует серверные сценарии и адаптеры, но не заменяет отсутствующие каталог аккаунтов, сервер и интерфейс устройств. Проверка cookie/CSRF и ограничения попыток входа должны быть подключены на реальном сервере.

**Проверка.** `session HTTP uses host cookies, CSRF checks and verified tokens rather than body identity`, `session HTTP rejects invalid routes, methods, input and CSRF, and preserves server failures`.
