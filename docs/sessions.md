# Вход, сессии устройств и отзыв доступа

Модуль `apps/api/src/modules/auth` добавлен в PR #10 по уточнению требований. Он соответствует разделам 01–02 `sapientum.drawio`: вход по логину и паролю, заранее созданные аккаунты, пять независимых ролей внутри турнира. Публичной регистрации нет. Обоснования — в [decisions/02-sessions.md](decisions/02-sessions.md).

## Когда пользователь теряет доступ

Проверка защищённого действия состоит из двух частей:

1. `auth` проверяет подпись, алгоритм, тип, issuer, audience и срок JWT, затем читает сессию и доступность аккаунта из БД/каталога. JWT содержит `sub` (аккаунт), `sid` (сессия), `jti`, `iat`, `exp`, `iss`, `aud`. Ролей и разрешений в нём нет.
2. Предметный модуль проверяет актуальное право аккаунта в нужном турнире через `StaffAccess`.

Снятие роли или исключение из оргкомитета действует **после коммита изменения, при следующей проверке права на любом устройстве**. Ждать истечения JWT не нужно. Сессия аккаунта остаётся открытой: например, человек может смотреть публичные команды или работать в другом турнире. Ответ при отсутствии права — 403.

Закрытие сессии действует **после коммита, при следующей аутентификации с этой сессией**, даже если JWT ещё не истёк. Блокируются все выпущенные для неё JWT и refresh-токены. Ответ — 401. Закрытие всех сессий действует на все входы аккаунта; новый успешный вход создаёт новую сессию.

Уже начатые операции не отменяются задним числом. Для подтверждения команды проверка права и изменение команды находятся в общей транзакции с блокировкой оргкомитета: отзыв прав ждёт завершения ранее допущенного подтверждения. Проверка сессии в HTTP-обёртке предшествует предметной транзакции; logout не отменяет запрос, уже прошедший эту проверку. Кэширования сессий и ролей здесь нет. Новые модули не должны проверять доступ только по подписи JWT.

## Устройства и сроки

Одна успешная авторизация создаёт отдельную сессию. Телефон и компьютер одного аккаунта получают разные `sid` и независимые цепочки refresh-токенов. Несколько вкладок одного браузерного профиля используют одну cookie и сессию; новый вход создаёт новую сессию. Метка устройства, User-Agent и IP нужны для отображения, а не для доказательства владения физическим устройством. Bearer-токен можно скопировать; аппаратной привязки здесь нет.

| Параметр          | По умолчанию     | Поведение                                                                               |
| ----------------- | ---------------- | --------------------------------------------------------------------------------------- |
| `accessSeconds`   | 900, 15 минут    | После истечения JWT требуется refresh; допустимы значения до 3600 секунд                |
| `idleSeconds`     | 604800, 7 дней   | Предел бездействия сессии; успешный запрос/refresh продлевает его до абсолютной границы |
| `absoluteSeconds` | 2592000, 30 дней | Максимум от первоначального входа; refresh не продлевает этот срок                      |

Все сроки задаются через `SessionPolicy` при сборке сервиса, в целых положительных секундах. Требуется `accessSeconds <= idleSeconds <= absoluteSeconds`, абсолютный срок — не больше 366 дней. Политика копируется и замораживается. Уже выданные сроки хранятся в БД/JWT: изменение настроек не сокращает их задним числом, для немедленного прекращения доступа нужно закрыть сессии. Максимального числа устройств пока нет.

Refresh — случайные 32 байта, в БД только SHA-256. Каждый refresh выдаёт новый access/refresh и помечает прежний refresh использованным. Повторное использование прежнего refresh закрывает всю соответствующую сессию. Использованные хэши сохраняются до удаления истории сессии. Ошибка клиенту возвращается после коммита закрытия, иначе откат вернул бы доступ. Одновременные refresh одного устройства необходимо объединять на клиенте: второй запрос трактуется как повтор, включая запрос из другой вкладки. При потерянном ответе с новым refresh потребуется повторный вход.

## Подключение и миграции

Из корня: `npm ci`, `docker compose -f infra/compose.yaml up -d`, затем `npm run typecheck` и `npm run test:coverage`. Тесты используют PostgreSQL и отдельные схемы, как описано в [teams.md](teams.md).

Миграции: `001-staff.sql`, `002-teams.sql`, `003-sessions.sql`. Новая миграция создаёт `auth_sessions` и `auth_refresh_tokens`; внешних ключей на ещё не реализованный каталог аккаунтов нет. При интеграции каталога нужен FK либо согласованная политика удаления и блокировки аккаунтов.

Пример сборки в сервере после применения миграций:

```ts
import {
  SessionService,
  PostgresSessionStore,
  JoseAccessTokens,
  secureSessionRuntime,
  createSessionRoutes,
  withSessionAuthentication,
} from './modules/auth/index.js';

const encodedKey = process.env.JWT_SIGNING_KEY_BASE64;
if (!encodedKey) throw new Error('JWT_SIGNING_KEY_BASE64 is required');
const codec = new JoseAccessTokens(
  Buffer.from(encodedKey, 'base64'),
  process.env.JWT_ISSUER ?? 'sapientum',
  process.env.JWT_AUDIENCE ?? 'sapientum-api',
);
// Реальные адаптеры каталога аккаунтов ещё предстоит подключить.
const store = new PostgresSessionStore(database, (sql) => accountModule.sessions(sql));
const sessions = new SessionService(store, accountModule.credentials, codec, secureSessionRuntime, {
  accessSeconds: 900,
  idleSeconds: 604800,
  absoluteSeconds: 2592000,
});
const handleAuth = createSessionRoutes(sessions);
const handleTeams = withSessionAuthentication(sessions, createTeamRoutes(teamService));
const handleStaff = withSessionAuthentication(sessions, createStaffRoutes(staffService));
```

`database`, `teamService`, `staffService` и фабрики предметных маршрутов в примере берутся из сборки соответствующих модулей. `accountModule` — обозначение будущего реального каталога, готовой реализации в проекте нет. В рабочем коде нет заглушки, принимающей любой пароль.

- `AccountCredentials.verify(login, password)` проверяет пароль заранее созданного аккаунта и возвращает его ID либо `null`. Хранение и проверка хэшей паролей, восстановление, блокировка перебора и создание аккаунтов — ответственность адаптера/будущего модуля аккаунтов. Пароль передаётся без trim и другой нормализации. Одинаковая ошибка входа используется для неверного пароля и недоступного аккаунта.
- `SessionAccounts.isEnabled(userId)` проверяется при входе, refresh и каждом защищённом запросе. Должен возвращать `false` для отсутствующих и заблокированных аккаунтов. Фабрика получает SQL-клиент текущей транзакции. При восстановлении доступности аккаунта незакрытая сессия может снова работать; для окончательного отзыва нужно закрыть все его сессии.
- Ключ HS256 должен содержать не меньше 32 **случайных** байт, храниться вне Git и совпадать у всех экземпляров сервера. Библиотека — `jose`; алгоритм фиксирован. Пароль или известная строка длиной 32 символа не заменяет случайный ключ. При замене ключа ранее подписанные JWT перестают проходить проверку; активные refresh остаются пригодны для выдачи нового JWT. Для полного отзыва закрываются сессии.

## HTTP-контракт и обязанности сервера

Это адаптеры, а не запущенный HTTP-сервер. Сервер должен разбирать JSON, извлекать Bearer access-токен из Authorization и передавать его как `accessToken` (пустая строка — нет токена). `withSessionAuthentication` сам создаёт `principal`; значение из тела запроса его не подменяет. Анонимный запрос передаётся предметному адаптеру, поэтому публичный список команд остаётся доступен.

| Метод  | Путь                 | Данные                                   | Результат                                                                |
| ------ | -------------------- | ---------------------------------------- | ------------------------------------------------------------------------ |
| POST   | `/auth/login`        | JSON: `login`, `password`, `deviceLabel` | 200, `AccessGrant` и новая refresh-cookie                                |
| POST   | `/auth/refresh`      | Refresh-cookie                           | 200, новый `AccessGrant` и заменённая cookie                             |
| GET    | `/auth/sessions`     | Bearer JWT                               | 200, все собственные сессии с состояниями `active`, `expired`, `revoked` |
| DELETE | `/auth/sessions/:id` | Bearer JWT                               | 204, закрыта своя выбранная сессия                                       |
| DELETE | `/auth/sessions`     | Bearer JWT                               | 204, закрыты все свои сессии, включая текущую                            |

`AccessGrant` содержит только `accessToken`, `sessionId`, `expiresAt`. Refresh не попадает в JSON. DTO экспортируются из `@sapientum/contracts/sessions`. Список показывает метку, IP, User-Agent, время создания, последней активности, сроки, отзыв и `current`. Чужие сессии не отображаются; попытка закрыть чужую возвращает тот же 404, что неизвестный ID. Права турнира не назначаются отдельному устройству: все сессии аккаунта используют его текущие роли.

Хост обязан применять `refreshCookie` ответа как cookie `__Secure-sapientum-refresh`: `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/auth`, без `Domain`, срок из `expiresAt`. `refreshCookie: null` удаляет cookie с теми же атрибутами. Закрытие текущей или всех сессий возвращает удаление cookie. Закрытие другого устройства не меняет cookie текущего. Access-токен браузер хранит в памяти; после перезагрузки получает новый через refresh-cookie. Нельзя сериализовать весь объект `SessionHttpResponse` как JSON: в нём есть служебное поле cookie.

Для мутаций, **включая login**, сервер проверяет точный разрешённый Origin и CSRF-токен и передаёт `csrfVerified: true` только после обеих проверок. Значение из тела/заголовка клиента само по себе не является результатом проверки. При `false` адаптер возвращает 403. Предметные мутации через Bearer требуют своей общей защиты на хосте; этот PR не запускает сервер и не реализует механизм выдачи CSRF-токенов. IP определяется соединением либо доверенной конфигурацией reverse proxy; произвольный X-Forwarded-For не используется как доверенный источник. User-Agent и метки — недоверенные данные отображения.

Все ответы auth имеют `Cache-Control: no-store`; сервер должен применить заголовок. Токены и пароли не должны попадать в логи. Неверные данные — 400, неверный/просроченный токен или закрытая сессия — 401, CSRF — 403, неизвестный маршрут/чужая сессия — 404, неподдерживаемый метод — 405. Сбои БД/каталога передаются серверу, а не превращаются в успешную авторизацию.

## Границы реализации

Готовы сценарии входа, выдачи и проверки JWT, ротации refresh, списка и закрытия сессий, PostgreSQL-хранилище и обёртка предметных маршрутов. Настоящий каталог аккаунтов, HTTP-хост, CSRF и интерфейс списка устройств ещё не реализованы; примеры не заменяют их подключение. WebSocket в схеме относится к табло; управление аутентифицированными долгими соединениями и повторная проверка прав при командах должны быть добавлены при реализации таких соединений. Уже загруженные данные удалённо из браузера не исчезают.

`apps/api/tests/sessions.test.ts` проверяет устройства, пароли без нормализации, приватность сессий, JWT, сроки, отзыв, ротацию, гонки через разные соединения, недоступность аккаунта и снятие роли на всех устройствах. Хранилище и криптография настоящие; каталог аккаунтов — явная заглушка тестов.
