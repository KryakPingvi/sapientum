# Оргкомитет и права

Модуль `apps/api/src/modules/staff` реализует членство существующего аккаунта в оргкомитете конкретного турнира. Создание аккаунта относится к модулю `auth` и здесь не выполняется.

## Поведение

- Пять независимых ролей: `jury`, `representative`, `author`, `administrator`, `organizer`.
- Администратор управляет составом оргкомитета. Организатор не получает это право автоматически.
- Членство уникально по паре `tournamentId + userId`, включая исключённых участников.
- Исключение сохраняет роли и историю, но немедленно прекращает доступ через `StaffAccess`.
- Повторное включение исключённого участника пока не реализовано. Добавление второй записи запрещено.
- Допускается действующее членство без ролей: оно не даёт разрешений на действия.
- Изменение ролей и исключение требуют `expectedVersion`. Устаревшая версия вызывает конфликт, чтобы два администратора не перезаписали изменения друг друга.
- Последнего действующего администратора нельзя исключить или лишить роли администратора.
- Запись участника и запись журнала фиксируются одной транзакцией. Ошибка журнала откатывает изменение участника.

## Границы и зависимости

`domain` содержит неизменяемую модель членства и локальные проверки. `application` зависит от интерфейсов хранилища, транзакций, каталога аккаунтов и источника времени/идентификаторов. `infrastructure` реализует хранение в SQLite. `http` преобразует запросы в вызовы сценариев.

Сценарии синхронные, как и выбранный SQLite-адаптер. `StaffTransaction.run` не допускает асинхронный callback. При переходе к асинхронному хранилищу нужно изменить контракты операций на Promise и обновить сценарии. Для первого модуля это сознательное упрощение; синхронный SQLite не выбран как обязательная БД всего турнира.

`BEGIN IMMEDIATE` получает блокировку записи до чтения прав и подсчёта администраторов. Поэтому два соединения не могут одновременно удалить обоих последних администраторов. Время ожидания блокировки — пять секунд. Конкурентная проверка выполняется двумя worker threads с отдельными соединениями.

## Подключение

После `npm install` доступны `npm run build`, `npm run typecheck`, `npm test`. Требуется Node.js 22.19+; используемый встроенный `node:sqlite` в Node 22 имеет экспериментальный статус.

Пример сборки модуля в серверном коде:

```ts
import { randomUUID } from 'node:crypto';
import { readFileSync, mkdirSync } from 'node:fs';
import { resolve } from 'node:path';
import { SqliteStaffStore, StaffService, AppointFirstAdministrator, createStaffRoutes } from './modules/staff/index.js';

// Пути задаёт приложение. Этот пример предполагает запуск из корня репозитория.
mkdirSync('data', { recursive: true });
const store = new SqliteStaffStore(resolve('data/staff.sqlite'));
store.migrate(readFileSync('apps/api/migrations/001-staff.sql', 'utf8'));
const runtime = { newId: randomUUID, now: () => new Date().toISOString() };

// accountDirectory — реализация AccountDirectory из модуля аккаунтов.
const service = new StaffService(store, accountDirectory, runtime);
const handleStaffRequest = createStaffRoutes(service);
const provisioning = new AppointFirstAdministrator(store, accountDirectory, runtime);
```

`AppointFirstAdministrator` вызывается внутренним сценарием после проверки существования турнира и прав владельца площадки. Назначает первому участнику роли администратора и организатора. Через публичный HTTP он недоступен. Проверка владельца и существования турнира должна быть реализована при подключении модуля турниров; здесь она не подменяется фиктивной авторизацией.

Аккаунты и турниры ещё не реализованы, поэтому миграция не содержит внешних ключей на их таблицы. Интеграция должна добавить эти ограничения либо обеспечить проверку через соответствующие модули.

## HTTP-контракт

Адаптер не запускает сервер. Сервер разбирает JSON, проверяет сессию и передаёт `principal: { userId }` либо `null`. Идентификатор пользователя берётся только из проверенной сессии; `actorId` из тела запроса не используется.

| Метод | Путь                                       | Тело / параметры                                        |
| ----- | ------------------------------------------ | ------------------------------------------------------- |
| GET   | `/tournaments/:id/staff`                   | `?status=active` или `?status=excluded`                 |
| POST  | `/tournaments/:id/staff`                   | `{ "userId": "...", "roles": ["jury"] }`                |
| PUT   | `/tournaments/:id/staff/:memberId/roles`   | `{ "roles": ["jury", "author"], "expectedVersion": 1 }` |
| POST  | `/tournaments/:id/staff/:memberId/exclude` | `{ "expectedVersion": 1 }`                              |

Все четыре операции требуют роли администратора выбранного турнира. DTO содержат идентификаторы пользователей; имена для отображения нужно получать из каталога аккаунтов.

Ошибки: 400 — некорректные данные, 401 — нет сессии, 403 — нет прав, 404 — участник/аккаунт не найден, 409 — конфликт версии, дубликат, исключённый участник или попытка удалить последнего администратора.

## Проверка прав в других модулях

`StaffAccess` получает только `StaffReader`, а не весь интерфейс записи. Соответствие разрешений ролям хранится централизованно: `staff.manage`, `reviews.check`, `answers.submit`, `tasks.manage`, `tournament.manage`.

Проверку нужно выполнять на сервере при каждом действии. Проверки прав по сохранённым в токене ролям не используются. Если операция другого модуля должна быть атомарной с проверкой членства, их следует выполнять в общей транзакции при интеграции.

## Проверки

Тесты покрывают изоляцию турниров, независимость ролей, отсутствие доступа после исключения, защиту последнего администратора, конфликт версий, откат при ошибке журнала, постоянное хранение данных, HTTP-валидацию и одновременные исключения через разные соединения.
