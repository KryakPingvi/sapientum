# Заявка и подтверждение команды

Модуль `apps/api/src/modules/teams` реализует issue #2, раздел 03 доски: подачу заявки, подтверждение организатором и публичные списки команд турнира. Архитектурные решения и принятые допущения описаны в [decisions/02-teams.md](decisions/02-teams.md).

## Поведение

- Руководитель под своим существующим аккаунтом подаёт заявку: название, организация, ФИО руководителя.
- При подаче проверяются существование турнира, открытая регистрация и существование аккаунта. Публичной регистрации аккаунтов здесь нет.
- `leaderId` берётся из проверенной сессии. Поля `actorId`, `leaderId`, статус и отметки подтверждения из тела запроса игнорируются.
- Заявка создаётся со статусом `pending`. Только действующий организатор этого турнира переводит её в `confirmed`.
- Подтверждение возможно после закрытия регистрации. Открытая регистрация требуется именно для подачи заявки.
- Подтверждение сохраняет время и аккаунт организатора. Повторное подтверждение возвращает конфликт, исходные отметки сохраняются.
- Название уникально внутри турнира без учёта регистра, включая подтверждённые команды. Пробелы по краям полей удаляются. В разных турнирах одинаковые названия допустимы.
- Один руководитель может подать несколько заявок с разными названиями. Редактирование, отзыв, отклонение и отмена подтверждения не реализованы.
- Название: 1–200 символов, организация и ФИО: 1–300 после удаления краевых пробелов. Пустые строки, значения других типов и нулевой символ запрещены. ФИО хранится строкой: число слов не проверяется.
- Списки открыты без сессии: все, подтверждённые и неподтверждённые. Они содержат поля `TeamDto`, в том числе организацию, ФИО и идентификатор руководителя.

## Подключение

Требуются Node.js 22.19+ и PostgreSQL. Установка и проверки из корня репозитория:

```sh
npm ci
docker compose -f infra/compose.yaml up -d
npm run format:check
npm run typecheck
npm run test:coverage
```

Адрес базы задаётся через `DATABASE_URL`, пример — в `.env.example`. По умолчанию тесты подключаются к `postgres://postgres:postgres@localhost:5432/sapientum_test`. Для каждого теста создаётся отдельная схема, после теста она удаляется. Нужны права на создание и удаление схем.

Миграции применяются в порядке `001-staff.sql`, затем `002-teams.sql`. Они создают отсутствующие таблицы и индексы; отдельного CLI миграций пока нет.

Пример сборки модуля в серверном коде:

```ts
import { randomUUID } from 'node:crypto';
import { readFileSync } from 'node:fs';
import { PostgresDatabase } from './infrastructure/postgres.js';
import { PostgresTeamStore, TeamService, createTeamRoutes, type TeamDependencyFactory } from './modules/teams/index.js';

const database = new PostgresDatabase({ connectionString: process.env.DATABASE_URL });
for (const name of ['001-staff.sql', '002-teams.sql']) {
  await database.migrate(readFileSync(`apps/api/migrations/${name}`, 'utf8'));
}

// Реальные accountModule и tournamentModule подключаются при реализации этих модулей.
// Их адаптеры должны работать в транзакции переданного sql.
const dependencies: TeamDependencyFactory = (sql) => ({
  accounts: accountModule.directory(sql),
  tournaments: tournamentModule.directory(sql),
});
const store = new PostgresTeamStore(database, dependencies);
const service = new TeamService(store, {
  newId: randomUUID,
  now: () => new Date().toISOString(),
});
const handleTeamRequest = createTeamRoutes(service);
```

`accountModule` и `tournamentModule` в примере обозначают будущие зависимости, готовых реализаций в проекте нет. В тестах используются явные заглушки, а оргкомитет и права работают с настоящей БД.

### Интерфейсы будущих модулей

- `TeamAccountDirectory.exists(userId)` возвращает наличие аккаунта.
- `TournamentDirectory.registration(tournamentId)` возвращает `{ open: boolean }` или `null`, если турнира нет. `open` обозначает возможность подать заявку, а не возможность подтвердить её.
- Фабрика зависимостей вызывается внутри каждой транзакции с её `SqlClient`. Реальный адаптер турниров должен удерживать совместимую блокировку состояния регистрации до конца транзакции. Например, чтение строки турнира с `FOR SHARE` не позволит закрыть регистрацию посреди подачи заявки. При интеграции нужно согласовать порядок блокировок с другими сценариями турнира: подтверждение сначала блокирует оргкомитет, затем читает турнир.
- Внешних ключей на аккаунты и турниры пока нет. При интеграции нужны FK либо согласованные правила проверки существования и удаления сущностей. Проверки через каталоги не заменяют защиту от конкурентного удаления.

## HTTP-контракт

Адаптер не запускает HTTP-сервер и не разбирает JSON. Сервер передаёт `principal: { userId }` из проверенной сессии либо `null`. Для GET сессия не требуется.

Для подключения к JWT и серверным сессиям используйте `withSessionAuthentication` из модуля `auth`; она проверяет сессию при каждом запросе и сама создаёт `principal`. Подключение входа, refresh и управления устройствами описано в [sessions.md](sessions.md).

| Метод | Путь                                     | Данные                                                                           | Результат             |
| ----- | ---------------------------------------- | -------------------------------------------------------------------------------- | --------------------- |
| GET   | `/tournaments/:id/teams`                 | `?status=all`, `pending` или `confirmed`; по умолчанию `all`                     | 200, массив `TeamDto` |
| POST  | `/tournaments/:id/teams`                 | `{ "name": "Сапиенты", "organization": "Школа 1", "leaderName": "Иван Иванов" }` | 201, `TeamDto`        |
| POST  | `/tournaments/:id/teams/:teamId/confirm` | тело не требуется                                                                | 200, `TeamDto`        |

Списки сортируются по времени подачи и идентификатору. DTO и тип запроса экспортируются из `@sapientum/contracts/teams`. Пагинации пока нет.

Ошибки имеют форму `{ code, message }`; у ошибок маршрутизации и отсутствия сессии может быть только `code`.

| HTTP | Коды                                                         | Причина                                                         |
| ---- | ------------------------------------------------------------ | --------------------------------------------------------------- |
| 400  | `INVALID_INPUT`                                              | Некорректные поля, идентификаторы, URL-кодирование или фильтр   |
| 401  | `UNAUTHENTICATED`                                            | Запись без сессии                                               |
| 403  | `FORBIDDEN`                                                  | Нет действующей роли организатора этого турнира                 |
| 404  | `USER_NOT_FOUND`, `TOURNAMENT_NOT_FOUND`, `NOT_FOUND`        | Нет аккаунта, турнира, команды в выбранном турнире или маршрута |
| 405  | `METHOD_NOT_ALLOWED`                                         | Неподдерживаемый метод известного маршрута                      |
| 409  | `REGISTRATION_CLOSED`, `DUPLICATE_NAME`, `ALREADY_CONFIRMED` | Закрыта подача, занято название или команда уже подтверждена    |

При подтверждении права проверяются до поиска команды, поэтому посторонний пользователь получает 403. Непредвиденные ошибки БД передаются серверу для его обработки, а не превращаются в ошибку пользователя.

## Транзакции и конкуренция

Уникальный индекс `(tournament_id, lower(name))` защищает от одинаковых названий при одновременной подаче. Только нарушение именно этого индекса преобразуется в `DUPLICATE_NAME`; другие ошибки БД сохраняются.

Подтверждение обновляет только строку `pending` выбранного турнира. Проверка права использует публичную операцию `requirePostgresStaffPermission` модуля оргкомитета, тот же SQL-клиент и ту же блокировку, что смена ролей и исключение. Изменение прав ждёт конца подтверждения; после исключения новые подтверждения запрещены. Доступа к таблицам оргкомитета из модуля команд нет.

## Проверки и границы задачи

`apps/api/tests/teams.test.ts` проверяет сохранение между соединениями, поля и их нормализацию, закрытую регистрацию, права и исключение организатора, изоляцию турниров, фильтры, конкурентные заявки и подтверждения, откат транзакции, ограничения БД и HTTP-контракт.

Отдельный конкурентный тест проверяет через `pg_locks`, что исключение организатора ждёт завершения подтверждения. Дополнение auth проверяет отзыв прав с действующими JWT на двух устройствах.

По уточнению требований в этот же PR добавлен модуль сессий, описанный в [sessions.md](sessions.md). HTTP-хост, веб-интерфейс, блокировки команд, рейтинг и печать ещё не добавлены. Блокировка и дисквалификация относятся к issue #3. Модуль турниров должен отдельно проверить конкурентное закрытие регистрации со своим настоящим адаптером.
